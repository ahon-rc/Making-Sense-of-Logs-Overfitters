## Possible cause

**HYPOTHESIS (most likely): a race between instance deletion and the image cache manager.**
1. The cache pass builds its list of instance disks on the host while the instance still exists.
2. In parallel, the delete request (req-49bcaa6b) renames `<uuid>/` to `<uuid>_del/` and removes it.
3. The cache pass then reaches `_list_backing_images` and runs `qemu-img info <uuid>/disk` on a path that no longer exists.
4. qemu-img exits with code 1 and ENOENT, and `qemu_img_info` turns that into `InvalidDiskInfo`.
5. Nothing in this call chain catches the exception, so it propagates to `run_periodic_tasks`. That pass is aborted and logged as an ERROR.

Evidence for this:
- In 3 of 8 occurrences the ERROR follows "Deletion of `<same uuid>`_del complete" by 18–46 ms.
- Stderr says "No such file or directory", not a format or permission error.
- The instance had spawned successfully 8.7 s before, so the disk did exist at some point.
- The cache pass appears to run about every 5 s. That is far more often than Nova's default interval as I remember it (2400 s; not verified from these logs), and it would widen the chance of hitting the window.

**Likely impact (HYPOTHESIS):** low. One cache pass is skipped and the next runs about 5 s later. The deleted instance's own lifecycle finished normally ("Took 0.46 seconds to deallocate network"), and the logs show no failure that a user would see. The logs can't show whether the skipped pass delayed base-image cleanup.

**Alternatives and how to tell them apart:**
- **A2: something outside this compute service deleted the files**, such as shared storage with another node, or an operator or script. This is weakened by the line "in use: on this node 1 local, 0 on other nodes sharing this instance storage" at 03:19:45.170, and by the matching local "Deletion of … complete" just before. To rule it out, every one of the 8 occurrences should have the same-uuid deletion within about 100 ms. Only 3 of 8 have been checked.
- **A3: the disk was never created or got lost** (failed spawn, filesystem problem). This is contradicted for 16797a0f by "Instance spawned successfully" at 03:19:36.619. It would show up as an occurrence with no delete request just before, or with an earlier spawn failure.
- **A4: a Nova version without a guard around this call.** It is consistent with A1 rather than competing with it. To check, see whether `_list_backing_images` at imagecache.py:309 has an `os.path.exists` check or an exception handler around `get_disk_backing_file`. If an existence check is there but the error still happens, that points to a check-then-use race. If there is no check at all, that points to a missing guard.
