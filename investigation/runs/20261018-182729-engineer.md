## Possible cause

**HYPOTHESIS (most likely): a race between the image cache manager and instance deletion.**
- The cache pass takes its list of instances, and the disk is still there for that check.
- Meanwhile the delete path renames `<uuid>/` to `<uuid>_del/` and removes it.
- By the time `qemu-img info <uuid>/disk` runs, the file is gone, so qemu-img exits with 1 and nova wraps that as `InvalidDiskInfo`.

Supporting evidence: in both occurrences I examined, the ERROR comes 18 ms and 24 ms after "Deletion of …_del complete" for the same UUID, and each traceback names a different UUID. The 5 s pass interval (OBSERVED) would make overlaps with deletes much more likely than nova's default interval would. That the interval is set low on purpose is also a HYPOTHESIS.

**Likely impact (HYPOTHESIS):** low. The error aborts one cache pass, and the next pass runs 5 s later. One side effect: if passes keep aborting, `_base` files may not be aged or cleaned up during that time.

**Alternative explanations, and how to tell them apart:**
1. **The disk really went missing for a live instance** (storage or shared-mount glitch, or a spawn that left no disk). If so, some of the other 6 UUIDs would *not* have a "Terminating instance" or "Deletion … complete" line just before their ERROR, and those instances would keep logging lifecycle events afterwards.
2. **Instance directory deleted outside nova** (manual cleanup or a script). In that case there would be no nova `Deleting instance files` line for that UUID near the ERROR.

I have only checked occurrences 1 and 8. Occurrences 2–7 have not been checked against deletes yet.
