## Possible cause

**HYPOTHESIS (most likely): a race between instance delete and the image-cache periodic task (TOCTOU).**
1. `_list_backing_images` gets its list of instance directories (or `all_instances`) while the instance still exists.
2. In parallel, the delete request (`req-49bcaa6b…` / `req-5cb8e158…`) renames `<uuid>` to `<uuid>_del` and removes it.
3. The cache manager then runs `qemu-img info <uuid>/disk` on a path that no longer exists. qemu-img fails with ENOENT, and nova wraps that as `InvalidDiskInfo`.

`_list_backing_images` does not handle a missing file, so the exception aborts the whole cache pass, which oslo logs at ERROR. This looks like a known class of upstream nova bug: the image cache doesn't tolerate instances deleted during the pass. Later nova releases catch this case. In both cases checked, the error came 18–24 ms after "Deletion … complete" for the exact UUID in the failing path.

**Alternatives and how to tell them apart:**
- **A. Disk deleted out-of-band** (operator, cleanup script, or storage issue) rather than by nova's delete. Under A you would see ENOENT with no nearby `Terminating`/`Deletion … complete` for that UUID. For the 2 cases checked there is a nova delete within 25 ms, which goes against A. The other 6 have not been checked.
- **B. Shared instance storage** (NFS) with another compute node deleting the files. Only one compute hostname appears in the context I looked at (`cp-1.slowvm1.tcloud-pg0.utah.cloudlab.us`), and imagecache reports "0 on other nodes sharing this instance storage". That goes against B, but I didn't count hosts across the whole dataset.
- **C. A real disk/metadata problem** (corrupt qcow2, permissions). Ruled out for these lines: stderr says `No such file or directory`, not a format or permission error, and `Stdout` is empty.

**Unknown:** whether skipping these passes ever delayed base-file cleanup in a way that mattered (filled `_base`). The logs don't show it.
