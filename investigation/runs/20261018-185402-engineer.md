## Possible cause

**HYPOTHESIS (main): a race between the image-cache periodic task and instance deletion.**
1. `_list_backing_images()` builds its list of instance disks before the delete happens.
2. In the same nova-compute process, the delete path destroys the domain, renames `/var/lib/nova/instances/<uuid>` to `<uuid>_del` and removes it.
3. The pass then runs `qemu-img info` on the old `<uuid>/disk` path, which no longer exists. qemu-img returns ENOENT, which becomes `InvalidDiskInfo`.
4. `_list_backing_images` does not catch that exception, so the whole pass aborts and oslo logs it.

Supporting evidence: in all 3 occurrences I checked, the ERROR comes 18–46 ms after `Deletion of …_del complete` for the same UUID. The deletes themselves completed, and the next imagecache pass about 5 s later ran normally.

**Likely impact (HYPOTHESIS):** each failure skips one cache-ageing/verification pass. I see no effect on users' VMs in these windows.

**Alternatives and how to tell them apart:**
1. **Disks really missing or storage faulty** (bad shared or NFS instance store, external cleanup). If so, errors would name *running* instances or appear without a nearby delete. Check whether occurrences 3–7 each have `Deletion of …_del complete` for the same UUID within about 1 s before the error (tool calls below).
2. **The prlimit sandbox (`--as=1073741824 --cpu=2`) killed qemu-img.** Unlikely: stderr says `No such file or directory`, not a memory or CPU error, and the exit code is 1.

**Unknown:** the logs don't show the exact `instances_path` layout, whether storage is shared, or the nova release. Only one node name appears, `cp-1.slowvm1.tcloud-pg0.utah.cloudlab.us`, in the resource_tracker lines of occurrence 1's window. The error lines carry no node field, so I can't confirm the host for all 8.
