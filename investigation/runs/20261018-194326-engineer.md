## Possible cause

**HYPOTHESIS: a race between instance deletion and the image-cache pass.**
1. `_list_backing_images` walks the instance directories it collected earlier in the pass and runs `qemu-img info` on each `<uuid>/disk`.
2. At the same moment, the libvirt driver's delete path renames `<uuid>` to `<uuid>_del` and removes it.
3. If the rename happens after the scan picks up the directory but before `qemu-img` runs, `qemu-img` gets ENOENT and nova raises `InvalidDiskInfo`.
4. The exception is not caught inside the image-cache manager, so the whole pass is aborted. `oslo_service` logs it and continues.

Evidence for this: in both occurrences I read, the error came 18–24 ms after "Deletion of …_del complete" for the same UUID, about 1 s after "Terminating instance".

**HYPOTHESIS (contributing factor):** the image-cache pass runs very often. Imagecache lines in the window recur about every 5 s (03:19:05, :10, :30, :35, :40, :45, :50…). Nova's default `image_cache_manager_interval` is 2400 s. A short interval combined with short-lived test VMs would make this collision likely. This inference is from the log timing only; I have not seen the config.

**Alternatives and how to tell them apart:**
- **The disk file was genuinely missing or orphaned** (failed spawn, manual cleanup, shared-storage desync). In that case you would *not* see a `Terminating` / `Deleting …_del` line for the same UUID within about 1 s before the error. NEXT CHECK: run the get_context calls below for the other 6 occurrences.
- **The prlimit wrapper killed qemu-img** (`--as=1073741824 --cpu=2`). This is ruled out for both occurrences I read. Stderr says `No such file or directory` and the exit code is 1, which is not what a resource-limit kill would produce.
- **Two compute processes share `/var/lib/nova/instances`**. The context interleaves two kinds of imagecache output for the same base file a489c868…: "in use: on this node 1 local" and, 5 s later, "Unknown base file … Removing base or swap file". That suggests either alternating passes or more than one image-cache manager. The logs here don't say which. Resolving it needs the hostname per line, which this dataset doesn't expose beyond the resource-tracker node name `cp-1.slowvm1.tcloud-pg0.utah.cloudlab.us`.

**Impact (HYPOTHESIS):** each failure skips the rest of that image-cache pass, so base-image ageing and verification don't happen for that cycle. I found no evidence of user-visible failures. The affected instances were already being deleted, and the next pass ran about 5 s later.
