## Possible cause

**HYPOTHESIS (most likely): a race between instance delete and the image-cache periodic task.**
1. `_run_image_cache_manager_pass` takes a list of instances on this host and scans the instance directories. That happens before the delete finishes.
2. `_list_backing_images` then calls `qemu-img info` on `/var/lib/nova/instances/<uuid>/disk` for each instance.
3. Meanwhile, the delete path renamed the directory to `<uuid>_del` and removed it (the "Deletion … complete" line), 18–24 ms before the error.
4. So `qemu-img` gets ENOENT and `get_disk_backing_file` raises `InvalidDiskInfo`. Nothing in `_list_backing_images` catches it, so the whole pass aborts and `oslo_service` logs the traceback.

Two things make the race window easy to hit:
- The pass appears to run about every 5 s here.
- The workload does fast create/delete cycles of about 30 s.

Likely impact: that one pass skips base-file aging. The next pass, 5 s later, ran without error.

**Alternative A: the disk is really missing or corrupt** (storage problem, manual removal, failed spawn).
- To tell them apart: a persistent problem would make the same UUID fail on every later pass until the instance is gone.
- What I saw supports the race: 8 errors, each a different UUID; one error per hourly bucket; no ERROR in the passes at 03:19:50 and 03:20:10; and every instance shown spawned successfully.

**Alternative B: shared instance storage**, where another host's delete removes files this node is scanning.
- To tell them apart: the imagecache lines say `0 on other nodes sharing this instance storage`, which argues against it.
- To rule it out, confirm `/var/lib/nova/instances` is local (`df -T`, or check for an NFS/Ceph mount).

**Not known from these logs:**
- The nova version and the exact upstream fix status.
- Whether a skipped pass ever left a stale `_base` file or caused a wrong removal.
- I did not confirm the "within ~25 ms of a delete" pattern for occurrences 2–7, only for occurrences 1 and 8.
