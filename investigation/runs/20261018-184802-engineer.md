## Possible cause

**HYPOTHESIS (primary): a race between the image cache pass and instance deletion.**
1. The pass builds its list of instances at the start. The instance being deleted is still on that list because the DB delete has not finished.
2. Meanwhile, the libvirt driver's delete path renames `/var/lib/nova/instances/<uuid>` to `<uuid>_del` and removes it.
3. When `_list_backing_images` (imagecache.py:309) reaches that uuid, it runs `qemu-img info` on a `…/<uuid>/disk` path that no longer exists. That gives ENOENT, which becomes `InvalidDiskInfo`.
4. The exception is not caught inside the image cache manager. It propagates up to `run_periodic_tasks`, which logs it and aborts the rest of that pass.

What supports this:
- In both cases I looked at, the error comes 18–24 ms after "Deletion of …_del complete" for the same uuid that appears in the qemu-img path.
- The stderr says ENOENT, not a permission or I/O error.
- The pass that followed ran normally and cleaned up the base file it had just "lost".

Impact appears to be cosmetic, limited to one skipped cache pass. That is an interpretation, and it is only checked for the first occurrence.

**Alternative A: the disk really was missing or unreadable on storage** (shared or NFS `instances_path`, a disk removed out of band, a mount glitch).
- Against it: every error coincides with a local delete of that uuid, and the base image reports `on this node 1 local, 0 on other nodes sharing this instance storage`.
- How to tell them apart: under Alternative A you would expect `qemu-img` failures for instances that were *not* being deleted, or errors other than ENOENT.

**Alternative B: the `prlimit` wrapper killed qemu-img** (`--as=1073741824 --cpu=2`).
- Against it: a prlimit kill would show a signal-style exit code and no "No such file or directory" message. Here the exit code is `1` with ENOENT.

**Not established by the logs:**
- I verified the delete correlation for only 2 of the 8 occurrences.
- I don't know whether any cached base image was wrongly removed because the pass aborted.
- I didn't measure how many compute hosts are present. The context windows only show `cp-1.slowvm1.tcloud-pg0.utah.cloudlab.us`.
