## Possible cause

**HYPOTHESIS (most likely): a race between the image cache periodic task and instance deletion.**

1. `_run_image_cache_manager_pass` (`req-addc1839`) builds its list of instances.
2. `_list_backing_images` then walks each instance's `/var/lib/nova/instances/<uuid>/disk` and runs `qemu-img info` on it to find its backing file.
3. Meanwhile, a DELETE on another greenthread (`req-49bcaa6b`) renames the directory to `<uuid>_del` and removes it.
4. `qemu-img` gets ENOENT. `qemu_img_info` turns that into `InvalidDiskInfo`. Nothing in `_list_backing_images` catches it, so the whole pass aborts and `oslo_service.periodic_task` logs it.

Supporting evidence:
- Deletion complete → ERROR is 18 ms and 46 ms in the two cases checked.
- Every one of the 8 errors names a different VM, and the missing file is always `disk`.
- This is consistent with a known upstream Nova bug where the image cache doesn't tolerate instances deleted mid-pass. That is from outside these logs; check it against your Nova version.

**HYPOTHESIS (secondary effect, unverified): the aborted pass loses track of a base image that is still in use.** About 5 s after the error, the same `req-addc1839` logged `Unknown base file …/_base/a489c868…` and then `Removing base or swap file …/_base/a489c868…`. Five seconds earlier that same file had been reported as "in use: on this node 1 local". The logs don't show whether any instance still needed it at removal time; it may just have been the deleted VM. If an in-use base file were removed, later spawns would have to re-download the image, or running copy-on-write VMs could be put at risk.

**Alternative explanations, and how to tell them apart:**

| Alternative | What would support it | What would rule it out |
|---|---|---|
| A. Storage/filesystem problem (NFS or shared `instances_path` flapping, or a lost mount) | ENOENT on disks of VMs that are *not* being deleted; errors not tied to DELETE timing; `qemu-img` errors elsewhere (spawn, snapshot) | Every occurrence sits within ~50 ms of a "Deletion of …_del complete" for the same uuid. Seen in 2 of 8; the other 6 need checking (see Next checks) |
| B. Something outside Nova removing instance directories (cleanup cron, `running_deleted_instance_action`) | ENOENT with no nova-api DELETE for that uuid beforehand | A DELETE 204 for the same uuid about 1 s earlier (true in both cases checked) |
| C. Corrupt or unreadable disk image | Stderr like `Image is not in qcow2 format` or `Permission denied` | All 8 Stderr lines say `No such file or directory`, so C is effectively ruled out |

**Still unknown:**
- Whether the aborted passes had any user-visible impact. Every VM involved was already being deleted, and the logs show no failed spawn or ERROR state.
- Which compute host or hosts logged these. The dataset has no host column on these lines. The resource-tracker line in the first window names node `cp-1.slowvm1.tcloud-pg0.utah.cloudlab.us`, but I haven't verified that for the other 7.

5. **NEXT CHECK – `/etc/nova/nova.conf` [DEFAULT] settings:**

6. **NEXT CHECK – on the host:** `grep -n "InvalidDiskInfo\|_run_image_cache_manager_pass" /var/log/nova/nova-compute.log*` to see whether this is still happening with current code and configuration.
